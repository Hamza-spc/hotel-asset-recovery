How a match happens

One Spring Boot process, seven Modulith modules. Kafka is the outbox for downstream consumers — matching, audit, and the live board listen in-process after the write commits.

  1. Someone writes a fact

    Housekeeping logs a found item, or a guest / front desk files a loss report. That is a domain command on an aggregate. Illegal status jumps throw before anything is saved.

  2. The transaction owns the outbox

    The same database transaction saves the aggregate and a Modulith event publication. If the commit fails, there is no half-published ItemLogged or LossReportFiled. After commit, listeners run and the event is also externalized to Kafka (lostfound.inventory, lostfound.claims, lostfound.matching).

  3. Matching embeds, then scores

    The matching module calls inventory and claims through public ports — it does not reach into their tables, so Modulith stays acyclic. Ollama nomic-embed-text writes a 768-d vector to pgvector. Combined score is 0.7 × text + 0.3 × spatial, where text is 1 − (embedding <=> embedding) and spatial is 1 − min(hypot / 40, 1). Missing coordinates contribute 0.5. Pairs below 0.52 are dropped.

  4. Staff decide. Guests do not.

    Duty managers see pending suggestions on /matches. Accept opens a claim and resolves the report; sibling suggestions are rejected. The guest receipt only shows status. Opening the inbox does not talk to Ollama — that would hide a timeout in a GET. Rebuild embeddings is an explicit manager action.
